# 对象存储元数据后端：关键假设的实测结论

> 本文记录一组针对「对象存储元数据后端」核心假设的实测结果。每条结论包含验证方法、
> 实测输出、结论与对设计的影响。结论仅在下述环境组合下成立。
>
> **环境**
> - opendal **0.59.2**，且 crate 家族（`opendal`、`opendal-core`、`opendal-service-s3`、
>   4 个 `opendal-layer-*` 及 transport）全部为 0.59.2，与仓库根 `Cargo.lock` 逐项一致。
>   仅声明 `opendal = "=0.59.2"` 不足以锁定：facade 对子 crate 是 caret 依赖，子 crate 会解析到
>   0.59.3，而**能力位定义在 `opendal-core`、S3 行为实现在 `opendal-service-s3`**。
>   验收命令（输出中不得出现 0.59.3）：
>   ```bash
>   cargo tree --manifest-path dev/objstore-toy/Cargo.toml \
>     | grep -oE 'opendal[a-z-]* v[0-9.]+' | sort -u
>   ```
> - MinIO `greptime/minio:2024`，由 `tests-integration/fixtures/docker-compose.yml` 启动
>
> **复现**
> ```bash
> # 依赖：MinIO 用 fixtures 的 compose 启动（卷中已有 bucket）
> cd tests-integration/fixtures && docker compose up -d minio && cd -
>
> # 版本验收（前置条件，见上）
> cargo tree --manifest-path dev/objstore-toy/Cargo.toml \
>   | grep -oE 'opendal[a-z-]* v[0-9.]+' | sort -u
>
> # 全量：ping + s0…s13、s15…s17（s8 输出 3 行：两幕 + 总判，s10 另有 3 行 [INFO]）
> cargo run -q --manifest-path dev/objstore-toy/Cargo.toml -- all
>
> # 单场景
> cargo run -q --manifest-path dev/objstore-toy/Cargo.toml -- s8
>
> # L1 的节点大小实测（不是场景，没有 PASS/FAIL）
> cargo run -q --manifest-path dev/objstore-toy/Cargo.toml --bin layout_probe
> ```
> `--manifest-path` 不可省略：`cargo` 按当前目录选择 workspace，省略时会开始构建整个 GreptimeDB。
> 场景自带 key 前缀并在结束时自行清理，重跑前无需重置 MinIO。
>
> **判定信号。** `PASS` 表示计划中写下的假设被实测证实，它不等于「系统安全」——
> 例如 S1 的 `PASS` 表示 ABA 洞确实存在。
>
> **可重复性。** `all` 连跑三遍，判定行全部 `PASS`。有几处刻意或天然的浮动：S0 的
> `landed=writer-A/B`、S10 第一幕的 `CAS 冲突` 次数（1–2）、S17 对照臂的绝对值
> （2684~2699，`27×` 这个比值稳定），以及带时长的那些数（S16 的重放耗时）。其余字段一致。`cfg.rs` 挂载了 opendal 的
> `RetryLayer`（理由见 S8 结论 ③；其边界由 S11 单独实测），`tokio` 启用了 `time` feature
> （S8 的延迟注入使用）—— 这两项不改变任何一条结论。

## S0 —— CAS 基本盘（0.59.2 回归 + 真并发）

**假设。** opendal 0.59.2 上 `if_match` / `if_not_exists` 的行为与 0.58 一致；
且两个写者持同一 etag 并发执行 CAS 时，恰好一胜一败。

**实测。**

```
[PASS] s0 CAS 基本盘: dup_create_rejected=true stale_write_rejected=true
        double_resign_rejected=true | 真并发 wins=1 conflicts=1 landed="writer-A"
```

顺序 6 步（抢锁 / 重复创建被拒 / 续租 / 过期写被拒 / resign 墓碑 / 重复 resign 被拒）全部符合预期。
真并发部分为两个 `tokio::spawn` 任务持同一 etag 同时写，结果 `wins=1 conflicts=1`，
且落盘内容为胜者的值。

**结论。** 无版本回归；条件写的原子性在真并发下成立。

**对设计的影响。**

- 条件写原语可直接作为「提交点」的基础，无需版本适配工作。
- 该结论依赖真并发验证。若「并发冲突」是在同一进程内**按顺序**再次调用造成的
  （旧 etag 自然与当前摘要不符），则该测试不构成并发验证。
  ⇒ 凡「并发安全」类结论，须确认测试中确为并发，否则属于自证。

## S1 —— ABA：CAS 无法识别「改两次又改回来」

**假设。** 由于 ETag 为内容摘要且**不单调**（A→B→A 之后旧 ETag 重现），
`if_match(e1)` 只能保证「**值**未变」，不能保证「**值**未被他人改动过**」。

**实测。**

```
[PASS] s1 ABA: e1==e4(旧ETag重现)=true 持有 e1 的写者在 A→B→A 之后 CAS 竟然成功=true
```

- `e1 == e4` —— 内容绕一圈回到 A，摘要随之回到原值（前提成立）
- 持 `e1`（A→B→A **之前**读到的 etag）执行 CAS ⇒ **成功**

**结论。** **ABA 洞确认存在。** 持有「读时 etag」的写者**无法察觉**对象在此期间被改过两次。
CAS 保证的是「值未变」，不是「值未被改过」。

**对设计的影响（一条承重不变量）。**

> **要让 CAS 等价于 fencing，被保护对象的值必须严格单调。**
> 值不重复 ⇒ ABA 不可能。这不是风格偏好，而是 CAS 能作为提交点的**前提条件**。

逐个对象核对：

| 对象 | 值 | 单调 |
| --- | --- | --- |
| `Manifest{epoch, committed_lsn, applied_lsn}` | 两个水位只增 | ✅ |
| `lease{holder, lease_until, epoch}` | 续租时 `lease_until` 只增；易主时 `epoch` +1 | ✅ |

⇒ 两者天然满足，**因此设计可以继续用 ETag CAS 保护它们**。
该判断现有实测依据，不再仅由推演得出。

**必须守住的边界**：任何**值可能重复**的对象都不能仅靠 ETag 保护。处置方式二选一：

1. 值中加入**单调递增的 bump 计数**（永不重复）；
2. 该对象改用 **epoch 语义**保护。

> 排查方法：以这条不变量遍历设计中所有走 CAS 的对象。
> 凡是「值可能回到历史状态」的（可回滚的水位、配置 blob、可复位的开关），都在该风险面上。

## S7 —— 条件删除：能力声明与实际行为不一致

**假设。** MinIO 对带 `If-Match` 的 DELETE **静默忽略** —— 过期 etag 照样返回 2xx 且对象真被删除。

**实测。**

```
[PASS] s7 条件删除: advertised=true stale_etag=true outcome=silently-ignored 删除后对象仍存在=false
```

三项均为关键证据：

1. **`advertised=true`** —— opendal 的 S3 后端**声明**支持 `delete_with_if_match`
   （`Capability::delete_with_if_match`）；
2. **`stale_etag=true`** —— 使用的确实是过期 etag；
3. **`outcome=silently-ignored` 且对象真被删除** —— 返回 `Ok(())`，条件被当作不存在。

**结论。** 比「API 不支持」更严重：**能力被声明，却未被执行。**
调用方若**只依据能力位判断**（最自然的写法：先查能力位再决定是否使用），
会得到「有保护」的错觉，而实际上**毫无保护**，且失败是静默的。

**对设计的影响（三条）。**

1. **删除一律走墓碑写**（以 CAS 覆盖成墓碑值），不使用 DELETE 的条件写 ——
   条件在 DELETE 上不可信。
2. **不能以能力位作为安全判据。** 能力位是「**声明**」，不是「**承诺**」。
   安全性质必须由**实测**确认，或由自实现的机制（墓碑 + CAS）保证。
3. **跨厂商调研的问法需调整。** 原本的问法「哪个后端支持条件写」会漏掉最危险的一类。
   正确的问法是：**逐 backend 检查 `*_with_if_match` / `*_with_if_none_match` 一组能力位
   与**实际行为**是否一致 —— 最危险的缺陷是 advertised-but-ignored**，
   而非 not-supported（后者至少会明确报错）。

> opendal 的契约中，服务未 advertise 时返回 `ErrorKind::Unsupported`。
> **不可将 `Unsupported` 读作「安全」** —— 那只是 **API 层门控**拦截，
> 换一个声明了该能力的后端即会落入静默忽略。判定须连 `advertised` 一并观察。

## S2 —— 分裂两步的顺序约束

**假设。** 分裂走「① `if_not_exists` 落右兄弟 → ② CAS 改左节点」时，
**中间态对读路径安全**（上半区的 key 仍可搜到）。

**实测。**

```
[PASS] s2 分裂中间态:
  | 正确顺序(先右后左) 中间态搜上半区key(30)=found(1跳) 下半区(10)=found(1跳) 补完第二步后=found(2跳)
  | 错误顺序(先左后右) 中间态搜上半区key(30)=不可达(2跳, 缺节点1) 下半区(10)=found(1跳) 补完第二步后=found(2跳)
```

**结论。** 顺序是**正确性约束**。正确顺序下中间态**完全可读**（左节点一字未动，
上半区 key 仍在其手中，1 跳命中）；顺序反向后，左节点先把自己改小、
并将 `right` 指向一个**尚不存在的节点** ⇒ 上半区 key **不可达**。

三条对照均为刻意设计，缺一条实验即不成立：

1. **错误顺序必须确实导致错误** —— 否则「先右后左」只是风格问题，对设计没有约束力；
2. **下半区必须仍然可读** —— 排除「整棵树都坏了」的解释，将危害**精确定位**到上半区；
3. **补完第二步必须自愈** —— 说明这是**窗口期**问题，不是永久损坏。
   但窗口期内读到的即为错误结果，对元数据层而言「短暂读到错的」与「错」等价。

> 注意判定中的 `不可达` 而非 `not found`：`Search::Unreachable` 与 `Search::Absent`
> 在 S2 中是**完全相反**的证据。若查找只返回 `bool`，错误顺序的中间态会表现为一个
> **看起来完全正常**的 `false`，本实验将静默地什么都没验出来。

**对设计的影响。**

- 分裂的两步顺序**固定为：先 create 右兄弟（`if_not_exists`），再 CAS 左节点**。
  这是正确性约束，不是可以优化掉的实现细节。
- 两步**不对称**：第一步是 **create**（创建原本不存在的对象，由 `if_not_exists` 提供互斥），
  第二步才是 **CAS**（修改已存在的对象）。设计文档需写明该不对称，
  否则容易实现成「两步都是 CAS」。
- ⇒ 崩溃安全设计的前提是「崩溃点落在第一步之后、第二步之前」，S3 验证的正是该点。

## S3 —— 分裂中途崩溃：孤儿无害，但必须 GC

**假设。** 在完成步骤 ① 之后崩溃，该右兄弟成为**无人指向的孤儿**，
但它**不丢数据，也不破坏查找**。

**实测。**

```
[PASS] s3 分裂中途崩溃: 全部key仍可搜=true 孤儿(节点1)仍存在=true 无人指向=true 目录可达链=[0]
        现场：节点0.keys=[10, 20, 30, 40] (high_key=None, right=None) | 节点1.keys=[30, 40] (high_key=None, right=None)
```

- **全部 4 个 key 仍可搜到**（左节点未被修改，上半区仍在其手中）；
- **孤儿节点 1 存在，但目录不路由到它，可达链 `[0]` 中也不含它**；
- 现场可见 `节点1.keys=[30,40]` 与 `节点0.keys` 的**上半区完全重复** ⇒
  孤儿是**冗余副本**，不是「丢失的数据」。

**结论。** 崩溃点选在此处（步骤 ① 之后）是**安全的**，但会留下**永久泄漏**：
没有任何指针指向该对象，它**不会被访问，也不会自行消失**。

**对设计的影响。**

1. **GC 是必需项，不是优化项。** 该判断从「读代码可推论」变为「有实测证据」。
2. **GC 的判据不能是「对象存在时间过长」。** 一个正在被读取的孤儿与真孤儿**无法区分**。
   唯一安全的判据是**从根做一遍可达性遍历**（mark-and-sweep 的 mark 阶段）。
   ⇒ 这本身是一个规模不小的模块，需在设计里单独立项。
3. **反过来，「先落右兄弟」的顺序使崩溃可被容忍** ——
   若顺序相反（先改左节点），崩在中间态即为**真正丢数据**（上半区不可达且无副本）。
   S2 与 S3 是同一条设计决策的两个侧面：S2 说明顺序不能错，S3 说明该顺序恰好使崩溃无害。

## S4 —— 「父指针可以延后修」的代价

**假设。** 父指针（此处为目录对象）**可以延后修，但不能永不修** ——
不修不丢数据，但查找成本退化为 O(链长)。

**实测。** 两棵**完全相同**的树（同样 key、同样分裂次数、同样顺序），
唯一差别是每次分裂后**是否重写目录**：

```
        分裂次数 | 节点数 | 不修目录: 查找跳数 | 修目录: 查找跳数 | 修的成本
               4 |      5 |                  5 |               1 | 每分裂 +1 次写(单点对象)
              16 |     17 |                 17 |               1 | 每分裂 +1 次写(单点对象)
              64 |     65 |                 65 |               1 | 每分裂 +1 次写(单点对象)

[PASS] s4: 两棵树查找结果都正确=true 不修目录的跳数随分裂增长=true 修目录的跳数=1(恒定)
        64 次分裂后: 不修=65跳 vs 修=1跳
```

**结论。** 「可以延后修」成立，**但「延后」必须有界**：
不修 ⇒ 跳数等于链长（**线性**）；修 ⇒ 恒定 1 跳。

**对设计的影响。** 这是一个真实的权衡，不是顺带的优化：

| | 不修目录 | 修目录 |
| --- | --- | --- |
| 查找成本 | O(链长)，64 次分裂后 65 跳 | 恒定 1 跳 |
| 写入成本 | 每次分裂 2 次写 | **3 次写**（+50%） |
| 争用 | 无 | 每次分裂都写**同一个对象** ⇒ 分裂者的热点 |

⇒ **「延后修」是用查找跳数换取写入争用。** 因此需要确定的不是「修不修」，
而是**多久强制修一次**（每 N 次分裂 / 链长超过 K / 后台定期）。
该阈值可依据上表两条曲线计算。

**适用范围与局限。**

- 这些数字来自**单层链**（无内部节点）。真实 B-link 树中，陈旧的父指针会把查找带到
  **目标附近**而非链头，因此**常数**会显著小于此处数值。
  应关注**形状**（线性对恒定），以及「修一次 = 多写一次单点对象」这一结构，
  **不应将 65 当作生产环境的跳数**。

## S5 —— 孤儿日志段：提交点不是「写成功」

**假设。** 日志段已 PUT、但 Manifest 的水位**未覆盖它** ⇒ 该事务对读者**不存在**。
恢复必须由 Manifest 驱动，**不能靠列举 bucket**。

**验证方法。** 构造一个孤儿段（写段、不推水位），
然后用**两种恢复方式处理同一份落盘状态**：

```
[PASS] s5 孤儿日志段: 桶里2个段/生效1个 | 按Manifest恢复含k2(孤儿)=false 按列举恢复含k2=true
       | 幂等写接管同一lsn=true if_not_exists重试被拒=true
       | 最终水位committed=3 恢复={"k1":"v1","k2":"v2-已接管","k3":"v3"} 缺失段=[]
```

**结论。** **「bucket 里有哪些对象」≠「哪些事务生效了」。**
同一份落盘状态、两种读法、两个结果：

| 恢复方式 | 结果 |
| --- | --- |
| 按 Manifest（只重放 `(applied, committed]`） | 孤儿段不进状态 ✅ 正确 |
| 按列举（重放所有可见段） | 孤儿段进入状态 ❌ 错误 |

该对照是实验的必要组成。只跑「按 Manifest」这一半，只能说明「代码没有去读孤儿段」，
对设计没有约束力；必须证明**同一份落盘状态换一种读法会得到错误结果**，
才能说明「提交点」这一概念是承重的。

**对设计的影响。**

1. **恢复路径只能由 Manifest 驱动**，实现中**不应出现任何「列 bucket 后重放」的代码路径**。
2. `Recovered` 中的 `missing` 字段（水位声称存在、段却不存在）**应当保留** ——
   它与「多出孤儿」是**完全相反**的两类故障：
   - 多孤儿 = 多余数据（安全侧，删除即可）；
   - 缺失段 = **确实丢失了已提交的数据**（危险侧，只能报错）。
   两者不可合并进同一个「恢复成功/失败」的布尔值。

## S5b —— 日志段必须幂等写，不能用 `if_not_exists`

**假设（最初的设想，后证实为错误）。** 「同一个 lsn 的日志段只应被写一次」⇒
使用 `if_not_exists` 防止重复写。

**实测。**

```
崩溃的写者留下的段：  已存在
重试同一个 lsn（if_not_exists） ⇒ Conflict ⇒ 恒 Conflict，永久卡死
同样情况下改用幂等覆盖写       ⇒ 接管成功（重写一次即可继续）
```

**结论。** 日志段**不是**提交点，Manifest 才是。给一个**非权威对象**加 `if_not_exists`，
等于**将一次崩溃从「可恢复」变成「永久卡死」**：崩在「段已写、水位未推」之间的写者，
会使**同一 lsn 的每一次重试都恒为 Conflict**。

**对设计的影响。**

- 日志段一律使用**幂等覆盖写**（普通 `put`，内容由 `(epoch, lsn)` 决定）；
  孤儿段因此可以被**接管**（重写一次即可继续）。
- 前提：**同一个 `(epoch, lsn)` 的内容必须唯一。** 该前提并非自动成立 ——
  违反会产生静默数据错误，见 S6 第二幕的构造性演示。
- ⇒ 设计上二选一：**lsn 由唯一定序者分配**（不能由各写者自行计算），
  **或**让日志段内容由 lsn 唯一决定（内容可复算）。两者至少取其一。

> 这条结论的反直觉之处：直觉是「防重复写 ⇒ 加 `if_not_exists`」，
> 而正确结论是「防重复写的前提是内容幂等，且条件写会把非权威对象变成权威对象」。
> 此类问题在纯设计推演中不易暴露，在实现阶段才会显现。

## S6 —— 提交点并发：Manifest CAS

**假设。** 两个写者持**同一个 etag** 并发 CAS Manifest ⇒ 恰好一个成功；**失败方必须不 ack**。

**验证方法。** 先让两个写者都把日志段落好（**同样的 lsn、同样的内容**），
再让它们持同一份 etag **同时**执行 CAS —— 这样把被测对象**隔离为提交点本身**，
不掺杂「谁先写段」的时序。两个 `tokio::spawn`，真并发。

```
[PASS] s6 提交点并发: 真并发CAS 胜=1 败=1 | 水位=2 == 胜者lsn(2)=true 单调递增=true
       | 生效事务=[1, 2] 只多了一个=true 基线仍在=true
       | 前提违反演示: A已ack=true 但生效内容是B的=true
```

**结论（两条）。**

1. **提交点的互斥由 Manifest 的 CAS 提供**，真并发下恰好一胜一败。

   败者拿到的是 `LostRace` —— 它是**独立枚举变体而非 `Err`**，因为
   「输了竞争」是**预期内的正常结果**（重试即可），不是错误；但**绝不能**被当作 ack。
   设计上**不提供** `is_success()` 这类会合并两者的方法，正是为了不给这个出口。

2. **S5b 中「内容唯一」这一前提，违反的后果已演示清楚**：一旦两个写者能以
   **同一个 lsn** 写入**不同内容**，就会出现
   「A 拿到 ack、Manifest 也确实提交，但**实际生效的是 B 的内容**」——
   反映到状态机上是**静默的数据错误**，而 A 侧看起来一切正常。

> **断言设计的一处修正。** 「生效事务」一项最初写作 `recovered.applied == vec![lsn]`，
> 实测 `FAIL`，但该断言中所有分项均为 `true`。原因是断言本身有误：场景开头为让水位非零
> 先提交了一个 `lsn=1` 的基线，重放 `(applied, committed] = (0, 2]` 本应得到 `[1, 2]`，
> 而 `== vec![lsn]` 隐含要求基线不存在。改为 `== vec![base.committed_lsn, lsn]`
> （即「恰好新增一个」）后通过。
> ⇒ 定量断言须同时断言「该测量本身有意义」；排查时若所有分项均正确、仅聚合断言失败，
> 应先检查断言而非系统。另外，第二幕中「哪一方获胜」在两边内容相同时本身不可观测，
> 可观测的只有水位与「恰好新增一个 lsn」，这也是断言须写成「多了一个」而非「是某一个」的原因。

**适用范围与局限。**

- 结论 2 的第二幕是**构造出来的交错**（顺序写死），**不是**观察到的竞态 ——
  实际跑出的竞态是随机的，无法作为稳定证据。构造它是为了明确「前提不成立时会怎样」，
  并非「实测到了该竞态」。

**与 S1、S5 的关系。** Manifest 的 `committed_lsn` **只增不减** ⇒
值永不重复 ⇒ **ABA 不可能** ⇒ ETag CAS 在此**安全**。S1 说明「CAS 需要值单调」，
S6 使用的是「水位恰好单调」，两者在此吻合。此外，输家的日志段**就是** S5 中的孤儿段 ——
水位不覆盖它，它就不生效。

## S8 —— 并发读写 + 并发分裂竞争

> 本条补 S2/S3 的证明力缺口：那两条验证的是**串行构造出来的**中间态
> （把状态摆成某个样子，再验证读是对的）。S8 验证的是：**真实并发下自然出现的**中间态，
> 同一条不变量是否仍然成立。

**假设（两条，分别对应 S2 与 S3/S6）。**

1. 写者持续分裂的同时，读者并发查询**已确认插入**的 key ⇒ **不会**拿到 `Unreachable`、
   **不会**查不到。即 S2 的「顺序承重」在真实交织下也成立。
2. 两个写者持**同一份 etag** 同时分裂同一个满节点 ⇒ 恰好一胜一败，
   且**败者能重试并收敛**（不是死路）。

**验证方法（两幕，证据类型不同）。**

**第一幕 · 并发读 + 单写者分裂。** 4 个读者 + 1 个写者（追加 24 个 key）。
关键在于**刻意不修目录**：目录永远指向节点 0 ⇒ 读者每次都从**最陈旧的入口**出发、
必须走完整条右兄弟链 ⇒ **必然穿过每一个正在分裂的节点**。
若修目录，读者会被直接路由到正确节点、绕过中间态，该实验将不验证任何内容。

读者只查询**已确认插入**的 key（写者 CAS 成功之后才记入共享列表）——
否则会退化为以「根本没有插入的 key」去查询，得到 `Absent` 却被当作失败。

```
[PASS] s8 第一幕 并发读+分裂: 读者4个共查200次 | 不可达=0 已插入却查不到=0 | 写者插入=24 分裂=11 冲突=0
```

**第二幕 · 并发分裂竞争。** 两个 `tokio::spawn` 持**同一份 etag**（同一个满节点、
同样的 4 个 key），各自用**不同的 right_id** 同时执行「① 落右兄弟 → ② CAS 改左节点」。

```
[PASS] s8 第二幕 并发分裂: 一胜一败=true(胜1/败1) | 左节点指向胜者=true 败者重试收敛=true
       | 败者看到的是胜者的结果=true | 败者的右兄弟是孤儿=true 树仍可搜=true
```

**结论（三条）。**

**① S2 的「顺序承重」不是串行构造的产物 —— 真实并发下同样成立。**
200 次查询中 **0 次不可达、0 次丢失已插入的 key**，而写者同时分裂了 11 次。
读者每次都被迫从最陈旧的入口走完整条链，因而**必然**穿过每一个正在分裂的节点。

**② 分裂冲突是「可恢复的」，不是死路。**
输家拿到 `Conflict` 之后**重读左节点**，发现 `high_key` 已有值（即已经分裂过），
于是收敛，不再反复覆盖。一条比 `converged` 更强的断言同样成立：
输家看到的**正是赢家那次分裂的结果**（`right == Some(赢家的 right_id)`）。
其成立理由是：该次 CAS 之所以失败，唯一可能就是赢家先落了盘。

⇒ **这一步在任何并发写路径中都是必需项，而 S2/S3/S4 的单写者代码中一次都没有出现**
（S4 的 `build_chain` 中 `cas_node(...).await?` 直接把 Conflict 作为错误抛出）。
这是 S8 相对前几个场景**新增的能力**，不是重复验证。

> 附带**复现了 S3 的孤儿**：败者造出的那个右兄弟（节点 2）**无人指向**，
> 可达链只有 `[0, 1]` —— 再次说明 **GC 是必需项**，且判据只能是可达性遍历。
> 该孤儿是**真实并发下自然产生**的，不是构造出来的。

**③ 瞬态传输错误是真实存在的，客户端必须自带重试层。**
首次运行即在两幕之间失败：

```
Error: Opendal(Unexpected (temporary) at read => send http request
   error sending request: client error (SendRequest): connection closed before message completed)
```

10 次中失败 **7** 次。这是**传输层**的瞬态（连接池中被服务端半关闭的 keep-alive 连接被重用），
与树结构、CAS 语义均无关 —— 但若把它当作 `FAIL` 报出，就是用环境噪声污染结论。

⇒ 在 `cfg.rs` 挂载 opendal 自带的 `RetryLayer`（它**只**重试 `Error::is_temporary()` 为真的错误）。
挂载后**未再失败**；瞬态本身并未消失，只是被吸收 —— 关闭 S8 的分裂延迟后重跑
（该延迟是触发它的时序），10 次中仍有 **9** 次记录到重试。

**该边界正是设计所需**：瞬态传输错误自动重试，而
**CAS 冲突 `ConditionNotMatch` 不是 temporary ⇒ 不会被这一层吞掉** ——
S1/S7/S8 中那些**刻意制造**的竞争仍能照常出现。

### 变异检查：竞态窗口宽度对采样充分性的影响

第一幕是变异检查的对象：把分裂两步**改反**（先 CAS 左节点、再落右兄弟），
读者应当观察到 `Unreachable`。**但未撑开窗口时实测只命中 1/6。**

原因是窗口的物理尺寸：改反之后，「左节点指向一个尚不存在的右兄弟」这一错误状态
存活时间只有**一次往返**（约 1.5 ms）。读者要命中它，必须恰好在这 1.5 ms 内走到该节点，
且查询的正是被搬到上半区的那两个 key。

⇒ 在两幕之间注入 **25 ms 延迟**（`SPLIT_GAP_MS`）以撑开窗口。该延迟
**对正确实现是语义中性的** —— 正确顺序下该窗口内的状态是「右兄弟已存在、左节点尚未修改」，
读者看到的是完整的旧节点，本来就安全；它**只**使错误顺序下的坏状态存活更久。

| | 正确顺序 | 变异（改反） |
| --- | --- | --- |
| 不注入延迟 | PASS 8/8 | **仅命中 1/6** ⇒ 采样不足 |
| 注入 25 ms | PASS 8/8 | **命中 6/6**（每次 7–22 次 `Unreachable`） |

⇒ 得到一条**关于并发测试本身**的结论：
**一次往返宽的竞态窗口，用几百次随机读去采样是不充分的。**
要么把窗口撑开（如本例），要么不应把此类测试当作回归网：
「跑了 200 次并发未出错」与「跑了 200 次并发、且窗口有 25 ms 宽也未出错」，
证据强度完全不同。

**适用范围与局限。**

- 第一幕**只有一个写者**。单层链只能尾插，两个写者并发追加**不同的 key** 会打乱链内的
  key 顺序 —— 这是**该原型结构退化**（无内部节点）导致的，不是设计的性质。
  真实 B-link 树依靠内部节点从根定位叶节点，天然支持并发插入，此处不对此作验证。
- 并发的**写**只在第二幕验证，且只针对「同一个节点的分裂」。
- 第一幕**没有反序对照组**是有意为之：其价值是**覆盖**（随机交织下出现各种中间态），
  **因果**由 S2 负责。上表是**核对**这一分工，不是替代 S2。

## S9 —— 条件读：`If-None-Match` 被服务端尊重（与 S7 的删除路径相反）

**被检验的假设。** 设计文档把「条件读」写进了对象存储原语表，用法是**"内容变了吗"的零传输探针**。
它成立的前提是"服务端真的执行了这个条件"，而这一点此前没有任何实测 ——
S7 已经证明**删除**路径上的 `If-Match` 被 MinIO 静默忽略，同一个问题必须对**读**路径单独问一遍。

**方法。** 同一个 key、同一个方法（`read_with().if_none_match(etag)`），只换 ETag 参数。
这组对照是**判别性**的：若后端静默忽略条件，两格都会返回内容；只有"当前 ETag"那一格能区分两种后端。

| 用的 ETag | 服务端尊重条件 | 服务端静默忽略 |
| --- | --- | --- |
| 当前（内容没变） | `ConditionNotMatch` | `Ok` + 内容 |
| 过期（内容变了） | `Ok` + 内容 | `Ok` + 内容 |

**实测**（连跑三遍一致）

```
[PASS] s9 条件读: advertised=true stale_etag=true 内容没变=condition-not-match 内容变了=returned(v2)
```

**结论。** 「内容没变 ⇒ `ConditionNotMatch`」成立 ⇒ **条件读可用**，探针名副其实
（省掉整份对象的传输）。

**对设计的影响。**

- 原语表里条件读那一行可以保留 ✅：S3 后端 advertise 了这一位
  （`opendal-service-s3-0.59.2/src/backend.rs:1060`），本场景确认它**不只是声明**。
- **更重要的一条是它与 S7 的对比**：同一个后端，**条件删除被忽略、条件读被尊重**。
  ⇒ 那个"advertise 了但忽略"的风险是**按操作**分布的，不是按厂商分布的 ——
  所以 §1 定下的研究动作（逐个 backend 核对那 6 组 `*_with_if_match` / `*_with_if_none_match` 位）
  不是走过场：**只能一个一个操作地核**，任何一条都不能从别的条外推。

## S10 —— 一个对象两个写者：`(值, ETag)` 必须同源

**被检验的假设。** 设计里 Manifest 有**两个写者各写各的字段**：提交路径写 `committed_lsn`、
applier 写 `applied_lsn`（§2.2 / §4.1）。两者都做 read-modify-write、都靠同一个 CAS 保护。
问：**CAS 保护的是哪个东西？**

答案是它只保证"**你交给它的那个 ETag** 还是当前版本"，**不检查**"你写回去的值是否与那个 ETag
同一次读出来的"。而 opendal 的 API 让这件事很容易做错：**`read` 只给值不给 ETag，
`stat` 只给 ETag 不给值** —— 想拿"值 + ETag"必须发**两次**请求，两次之间对象可能被改。
于是**顺序**成了承重结构：

| 取的顺序 | 中间被改时拿到 | CAS | 后果 |
| --- | --- | --- | --- |
| `stat` → `read`（先 ETag 后值） | 旧 ETag + 新值 | **失败** | 安全，重试即可 |
| `read` → `stat`（先值后 ETag） | 旧值 + 新 ETag | **成功** | ⚠️ **写回旧值 ⇒ 静默回退对方字段** |

**方法。** 三幕，前两幕缺一不可：

1. **真并发**：两个写者并发各跑 8 / 5 轮，都用 `stat → read` + CAS + 冲突重试。
2. **变异**：单写者用 `read → stat`，并在两次请求**之间**让另一方改掉对象。
3. **对照**：同样的中间改动，但写者用 `stat → read`。

**实测**（连跑三遍一致；第一幕的冲突次数在 1–2 之间浮动 —— 那是真并发的迹象）

```
[INFO] s10 第一幕 真并发（stat→read + CAS + 冲突重试）: A 成功 8/8 轮、B 成功 5/5 轮、CAS 冲突 1 次 ⇒ 最终 committed=8（期望 8）applied=5（期望 5）⇒ 两个字段都到齐
[INFO] s10 第二幕 变异（read→stat，中间被改）: CAS 成功 、committed 4 → 3 ⇒ ★ 对方的字段被静默回退
[INFO] s10 第三幕 对照（stat→read，中间被改）: CAS 被拒 、committed 4 → 4 ⇒ 被拒且不回退（代价只有一次重试）
[PASS] s10 一个对象两个写者: 并发两种顺序下字段都到齐=true 反序会静默回退=true 正序只丢一次 CAS=true
```

**结论。** 「一个对象、两个字段写者」在 CAS 之上**不是自动安全的**：第二幕是**确定性构造**出来的失败
——CAS **成功**、`committed` 从 4 被写回 3，而两个写者谁都没违反任何 CAS 契约。
第三幕给出代价上界：顺序对了，就只是一次 CAS 失败。

**对设计的影响（要落到 M3 的 Manifest 读写封装里，不能留给调用方自觉）。**

1. Manifest 的"读"必须是 **`stat` → `read`** 这个顺序；反过来会在并发下静默回退对方字段。
2. `(值, ETag)` 必须当作**一个快照**传递（封装层不提供"分开取"的接口）。
3. §4.3 那句"写者收敛为唯一的 applier"因此**不是**可有可无的优化：即使两个写者都守规矩，
   "两个字段各写各的"也要求每次写回都带上对方的**当前**值，而那份"当前"只有这个快照能给。

**诚实边界。** 第一幕的变异检查（把 CAS 换成无条件 `put`）**只 2/3 命中**：连跑三遍得到
`committed=8 / 0 / 0` —— 其中一遍两个写者的时序没有交叠，坏状态就没被看见。
这与 S8 那条教训同源（窗口太窄 ⇒ 采样不足）：**第一幕的价值是覆盖，因果由第二/三幕的确定性对照负责。**

## S11 —— 重试层边界：只吸收瞬态，不吞 CAS 冲突

**被检验的假设。** `cfg.rs` 挂的 `RetryLayer::default()` **只**重试 `Error::is_temporary()` 为真的错误
（`opendal-layer-retry-0.59.2/src/lib.rs:139`）⇒ 刻意制造的 CAS 冲突**不会**被它重试，
应当每次都原封不动地冒上来。

为什么必须实测：设计把"网络抖了一下"和"我并发输了"当成**两条动作相反的路** ——
前者该由基础设施层自动吸收，后者必须能分辨、并交给上层的"重读 → 收敛"。
若这层把两者混在一起，`LostRace` 就没法是个**独立变体**（§3.3）。

**方法。** 20 次**带过期 ETag** 的条件写，读 `cfg::transient_retries()` 计数器的前后差。
取 20 次是为了让"零重试"不像偶然。

**实测**（连跑三遍一致）

```
[PASS] s11 重试层边界: stale_etag=true 20 次过期写 → Conflict 20 / 落盘 0 / 被重试 0 次 ⇒ 值未被改动=true
```

**结论。** 20/20 全 `Conflict`、**重试计数增量为 0**、20 次过期写一个字都没落盘。

**对设计的影响。**

- M1 要的那条边界，两半各有实测：**瞬态被吸收**由 S8 提供（关掉注入延迟后 10 次里 9 次记到一次重试），
  **冲突不被吞**由本场景提供。合起来才是"只重试瞬态"。
- ⇒ `ConditionNotMatch` / `LostRace` 可以放心做成**独立变体**：不会有什么中间层把它变成"重试后成功"。

**诚实边界。** 本场景**没有**做外部变异检查 —— 层的重试判定在 opendal 内部，
除非另写一个 interceptor，没法把它改成"连冲突也重试"。所以"冲突**不会**被重试"这条的强度，
来自**计数器的直接读数**（0 次）+ S8 对同一计数器的正向印证（瞬态**会**让它 +1）。

## S12 —— CAS 失败之后：分类够不够？

**被检验的假设。** CAS 失败后重读 Manifest、比对 `epoch`，**只能分出「被 fenced」**；
「我赢了但 ack 丢了」与「输给并发」在 Manifest 上**完全同形**，分不开。

为什么这条要紧：设计里 `LostRace` 是**独立变体**（S6 的结论），而「日志记结果不记意图」
要求**幂等重放** —— 两者都要求调用方能说出自己是哪一种失败：

1. 「被 fenced」⇒ 本次任期作废，**不能**重试；
2. 「输给并发」⇒ 换个 lsn 重试；
3. 「我其实赢了、只是没收到 ack」⇒ **重试是错的**，应该直接确认。

后两种若不可分，幂等重放就做不出来：会把一次**已经成功**的提交当成失败重做，
或者把别人的结果认成自己的。

**方法。** 五幕，每幕自建前缀（`toy/s12/{fenced,applier,race,replay}`）。前三幕让四种历史
各自发生一次，把重读到的 Manifest 喂给一个**纯函数** `classify()`（只看 `epoch` / `committed_lsn` /
`applied_lsn` 三个字段），看它判成什么；幕四**故意丢掉成功那次的返回值**（= ack 丢失），
再让调用方拿旧快照重放 —— 这正是幂等重放要处理的时序。幕五给 Manifest 加一个
`last_writer` 字段，把同一个纯函数改成四分支，验证"出路"是否真的可行。

**实测**（连跑三遍一致）

```
[PASS] s12 CAS 失败分类: 幕一→被 fenced（本任期作废） | 幕二→重试即可 | 幕三→★ 分不清：别人抢先 / 我自己赢了但 ack 丢 | 幕四→★ 分不清：别人抢先 / 我自己赢了但 ack 丢 | 幕三==幕四=true 水位逐字段相同=true | 各幕的CAS确实被拒: 幕一=true 幕二=true 幕三=true 幕四=true | 对手赢=true 我第一发赢=true | 加归属后可分=true
```

**结论。**

- **可靠分辨**的只有前两类：「被 fenced」（`epoch` 变了）与「重试即可」（水位没到我这一格）。
- 「输给并发」与「我赢了但 ack 丢了」落在**同一个分支**上：两种情况 `epoch` 都没变、
  `committed_lsn` 都 `>=` 我这一格 —— 不只判定相同，两份 Manifest **逐字段相同**。
- ⇒ **`LostRace` 这个二分类不足以支撑幂等重放**。调用方无法回答「我该重试，还是我其实已经成功了」。
- **出路有两条，幕五实测第一条可行**：
  1. Manifest 多记一个「水位最后被谁推的」（本场景用法：`last_writer`）⇒ 幕三/幕四分开；
  2. **让 lsn 由唯一定序者分配** —— 那样某一格只可能属于一个人，水位越过我这一格就等于「我赢了」。
     注意这条与 **S6 第二幕**的结论是**同一条**（同一个 `(epoch, lsn)` 的内容必须唯一，
     否则段会被互相覆盖）。

**对设计的影响。**

- 设计里的 **Q11「lsn 由谁分配」正是问这个** —— 它不只关乎日志段会不会被互相覆盖，
  还直接决定 CAS 失败能不能被幂等重放。这两件事在 toy 里汇到了同一条约束上。
- **在此之前，「重试一次提交」在对象存储后端上不是幂等的**。这条要写进 §3.3 的边界，
  不能只说「`LostRace` 是独立变体」就交差 —— 独立变体只解决了「不把输当成成功」，
  没解决「不把成功当成输」。

**变异检查**（每条完整还原并复跑基线）

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| ① 幕四不丢 ack（重放前先取新 etag） | 幕四不再被拒 ⇒ 不能与幕三同形 ⇒ FAIL | ✅ `[FAIL]`，`幕四=true` 的 CAS 未被拒 |
| ② `classify_owned` 忽略 `last_writer` | 幕五分不开 ⇒ 出路①是假的 ⇒ FAIL | ✅ `[FAIL]`，`加归属后可分=false` |
| ③ 幕二 applier 根本不推（`applied_lsn` 不动） | 我的 CAS 应当**成功** ⇒ 幕二不成立 ⇒ FAIL | ✅ `[FAIL]`，`幕二=false` |

三条都红了，说明 `pass` 不是恒真的：每一幕都有独立的断言在撑着。

**诚实边界。** 幕三与幕四各自只跑一次，"两者同形"是**构造出来的**而非统计出来的 ——
但这不是采样问题：`classify` 是纯函数，两次输入的两份 Manifest 是**逐字段相等**的
（`水位逐字段相同=true`），所以同形是**结构性的**，重跑多少次都一样。
副作用是"幕三==幕四"这个布尔值本身会读着像恒真式 —— 为此打印行里另给了两个信号
（`幕三/幕四的 CAS 确实都被拒`、`对手赢`、`我第一发赢`），证明两边的**历史不同而结论相同**。

## S13 —— 一次 txn 到底多大？

**被检验的假设。** 真实 DDL 的一次 txn **远小于**候选段大小 ⇒ 日志段永远装得下一个 txn
（设计 §3.5），**不需要**「一个 txn 跨多段」那套东西。

为什么这条要紧：设计把 `max_txn_ops` 从存储层的**硬**约束（etcd 的 128 op）**降级为段大小的软参数**，
但当时没写清"软参数超了怎么办"。要么它超不了（本场景验这个），要么就得有跨段方案。

> **⚠️ 口径更正（2026-10-15，导师口径）。** 「超了怎么办」这个问题本身不需要答案：
> **段大小是「攒批凑到这个量就提交」的目标值，不是上限。** 超过它的单个事务自己占一个段、
> 单独提交，原子性仍然来自 Manifest 那一次 CAS ⇒ 段多大不参与任何正确性判断。
> 所以本场景量出来的"一次 txn 有多大"仍然有用（它决定一个段最大会长多大、一次提交的写有多重），
> 但它**不再是一个需要被遵守、超了要有对策的界** —— 下面「对设计的影响」里那三条路随之作废，
> V2b 也不做。

**方法。** **不连对象存储**，纯字节数：真实编码是 JSON（`MetadataValue::try_as_raw_value`
→ `serde_json::to_vec`），字节数**对字段名敏感** ⇒ 把真实结构**逐字段照抄**（连 serde 属性一起），
只把值的**规模**参数化（`R` region 数 / `D` datanode 数 / `C` 列数），按 `key.rs` 的真实形状
合成最坏情况，再量 `create_table_txn_payload()` 的字节数。三个规模参数独立扫。

照抄的细节里有两处**不是装饰**：`RegionRoute.leader_down_since` **没有** `skip_serializing_if`
（`leader_state` / `write_route_policy` 有）⇒ 这种不对称真的多几个字节；
`region_wal_options` 的**值是 JSON 字符串**（`wal_provider.rs` 的 `serialize_region_wal_options`）
⇒ 外层 JSON 要**再转义一次**，每个 region 都多付几个字节。

          载荷对 region 数是**严格线性**的（每 region 递增 524B，不是平方），
          所以「一个 txn 撑爆一个段」在小表上不是问题。
        ⇒ 结论二：单个事务**可以很大**，而且大多少算得出来。
          256KB 在「172 个 region × 10 个 datanode」处就被一个建表事务自己顶满 ——
          那是分区表 / repartition 之后真能到的量级（1000 region × 100 datanode 是 10994.2KB）。
          ⇒ 但这**不是限制**：段大小是「攒批凑到这个量就提交」的目标值，不是上限。
             超过它的单个事务自己占一个段、单独提交，原子性仍然来自 Manifest 那一次 CAS，
             段多大不参与任何正确性判断 ⇒ 不需要跨段方案，也不需要写入路径上的检查。
          ⇒ 这个数真正说明的是：攒批对建表事务几乎不起作用 —— 上百 region 的建表，
             一个事务自己就顶满了（对照：默认规模 1 region 才 3.2KB）。
        ⇒ 放大项的归属：不是 route，是 `region_wal_options` 被**每个 datanode 复制一份**
          （`O(R·D)`，`datanode_table.rs` 里的 FIXME 自己承认了这个冗余）。
          每 region 的原始字节数由表的 WAL 形态决定：raft_engine 30B、object_store 91B、kafka 82B ⇒ 换 WAL 形态就是给
          这个大小乘一个系数；上表按其中最大的 object_store 报。
```

**结论。**

- **结论一（默认规模下这个担心不成立）**：不分区、单 datanode 的一次建表 txn 约 **3.2KB**；
  载荷对 region 数是**严格线性**的（每 region 递增 524B，不是平方）。所以「一个 txn 撑爆一个段」
  在小表上不是问题。
- **结论二：单个事务可以很大，而且大多少算得出来。** 256KB 在「172 个 region ×
  10 个 datanode」处就被一个建表事务自己顶满；那是分区表 / repartition 之后真能到的量级
  （1000 region × 100 datanode = **10.7MB**，最坏 WAL 形态）。
  **但这不构成限制** —— 见开头的口径更正：段大小是攒批的目标值。这个数真正的用处是说明
  **攒批对建表事务几乎不起作用**（上百 region 的建表，一个事务自己就顶满了）。
- **放大项的归属不是 route，是 `region_wal_options`**：它存的是**整张表**的 per-region wal options
  （`datanode_table.rs` 里的 FIXME 自己承认了这个冗余），而它**每个 datanode 一份** ⇒ 这一项是
  `O(R·D)`。表里 1000×10 那一行 `dn_tables` 425KB 对 `route` 375KB 还看不出来，1000×100 时
  `4213KB` 对 `390KB` 就一目了然了。它是"一个段最大会长多大"的主导项。
- **每 region 的原始字节数由表的 WAL 形态决定**：raft_engine **30B**、object_store **91B**、
  Kafka **82B** ⇒ 换 WAL 形态就是给这个大小**乘一个系数**（3 倍），不是换个量级。
  **最坏形态是 object_store，不是 Kafka** —— 上一版把最坏形态写死成 Kafka，报出去的数因此
  不是最坏情况（见下面的诚实边界）。
- 代码里**没有任何**对 value 字节数或 txn 总字节数的显式校验（既有上界全部与字节数无关：
  `max_txn_ops=128` 是 op 数、etcd 32MB 是解码上限、gRPC 512MB、MySQL key ≤3072B / value ≤16MB）。
  按新口径这**不需要补**：既然段大小不是上限，写入路径就不该有一个按字节数的拦截。

**对设计的影响。**

- **§3.5 的「段大小是软参数」这个说法要改成"攒批的目标值"**：它不是上限，超了既不拒绝也不切分
  —— 一个事务自己占一个段。**原定的三条路（段大小取大 / 保留跨段 txn / 写入路径报错）全部作废**，
  V2b 不做。
- **仍然要写进设计的一条**：这个数决定"一个段最大会长多大"（实测最坏 **10.7MB**）。
  它影响一次提交的写有多重、CAS 冲突时重写多贵，但不影响正确性。
- **唯一还剩下的硬边在存储层**：单对象直传有大小上限，超过就得走分段上传，而分段上传
  **不是一次原子写入** —— "段 = 一个对象 = 一次原子写"这个前提到那里才会真的破。10.7MB 离那条线
  还很远，所以设计里只需记一句"上限在存储层、不在我们这一层"。
- **这条正好补上 §10.1「哪些论断有实证支撑」表里的一个空行** —— 之前没有 txn 大小这一项。
- **修正一个容易讲错的定性**：把 `region_wal_options` 说成"顺带的元数据"是错的，
  它在合并 txn 里的**权重随规模反超 route**，是"一个段能长到多大"的主导项。

**变异检查**（每条完整还原并复跑基线）

| ① 默认列数 10 → 1000 | 默认规模不再"可忽略" ⇒ FAIL | ✅ `[FAIL]`，`默认小到可忽略=false` |

**诚实边界（一次真实的"检查器自己需要被检查"）。** 变异③ 第一次用的是**平方项**
（`0..regions*regions`），跑出来 `[FAIL] 对R线性=true` —— **斜率逐次翻倍（40895/82296/165996）
而断言照样报 true**。原因是第一版写的是
`let (lo, hi) = (这三个斜率自己的 min*0.99, max*1.01)`：**区间由这三个数生成，它们必然全落进去**，
这条检查**恒真**。恒真的断言比没有断言更坏，因为它看起来在被检查。
改法是以**第一个斜率当基准**逐个比（`(s / s1 - 1.0).abs() < 0.01`），随后那次重跑还因为
平方项把扫描表 `(1000, 100)` 那一行推成 `10⁸` 个 map 项而**挂死**（`timeout` 杀掉），
于是换成**有界**的超线性扰动（`R + R²/32`，R=1000 时只多 31250 项）才跑出上表那行的干净 FAIL。
两个副产物：`crossover_regions` 不能线性扫描（那是 `O(R²)`），改成两点外推 + ±4 复测；
复测前加 `MAX_PROBE_REGIONS` 上限保护，估计值离谱时直接报"外推值过大，不再实测"。

另一条边界：`table_info_value_bytes` 按真实样例取 **≈280B/列**，是本文件**唯一**的近似
（其余字段都是逐字段照抄）—— 但它只影响 `table_info` 那一列，而那一列在这次结论里**不是**放大项
（2.4KB 恒定），所以不影响任何一条结论。

**还有一条：错在自己打出来的证据里。** `crossover` 那四档原先按 **Kafka** 形态算
（183/736/3692/23667），而同一个文件打出来的 `wal_forms` 明明是 **object_store 91B** 更大
（Kafka 只有 82B）—— 也就是说报出去的数**不是最坏情况**，而"最坏形态"这四个字还印在输出标题上。
根因是**写死**：`crossover_regions(.., WalKind::Kafka, ..)` 与 `fits_256k` 都硬编码了形态。
改法不是把 Kafka 换成 object_store（那只是换一个写死），而是从 `wal_forms` 里 `max_by_key` 自动取，
并把结论文案里引用的数改成从 crossover 表里查（`cx(limit)`），一处都不再写字面值。
改正后是 **172/693/3471/22254**，最坏一次建表从 4.6MB（RaftEngine 那一行的口径）变成 **10.7MB**。

## S16 —— 恢复要多久？

**被检验的假设。** 设计 §10.1「哪些论断有实证支撑」那张表里，**只剩一行没实测过**：
`recovery ≤ f(MAX_UNAPPLIED)`，状态栏写着「**分析模型，非实测**（依赖 §3.3 还没定的攒批参数
⇒ M4 定下来后复核一次）」。而 §5.4.4 的 failover 分解已经**在前一句就用上了它**：
`T = 5s 时 ≈ 8~10s`。本场景就是去把这一格从「分析模型」变成「实测」，
顺便看看那句「M4 定下来后复核一次」到底该复核出什么。

**方法。**

- 走**真实路径**：`CommitLog::recover_by_manifest`（读 Manifest → 从 `applied_lsn + 1` 到
  `committed_lsn` 逐段 GET），**不是** S5 已证是错的那条 `recover_by_listing` 捷径。
- 阶梯是 `n / 4n / 16n` 三档，而 **n 由幕〇实测的写/读单段耗时算出来**（目标：最大档一次恢复
  落在 30s 预算内），不写死。换机器、换后端，阶梯会自己变，判定比值不变。
- 运行时断言**段对象 < 64KB**（`TRANSFER_NEGLIGIBLE_BYTES`）：只有每段小到传输项可忽略，
  L1 的加性结论（`GET ≈ 截距 + 字节/带宽`）才成立，本机数字才能按「每跳延迟」平移到真 S3。
  这条前提**每次运行都查一遍**，不留给读代码的人自己记。
- 幕二**固定总量、只改 applied 水位**：同样是两万多段，一份 applied 停在 `n − 128`、一份停在 0。

**实测**（连跑三遍一致）

**结论。**

- **结论一（§10.1 那一格可以填了）**：恢复耗时对段对象数**严格线性**，实测比值
  **1.0 / 3.9 / 16.1** 对设计比值 **1 / 4 / 16**，偏差 ≤ 2.5%。
  这一格从「分析模型」升级为「实测」，而且测的是**最坏形态**（顺序读、不并发）。
- **结论二（更要紧的那条：窗口由水位定，不由总量定）**：同样 22832 段，只重放 128 段是
  **0.174s**，全量是 **30.28s** —— **差 174 倍，而两次读的是同一份日志**。
  ⇒ §6.1 把 `MAX_UNAPPLIED` 当启动窗口的旋钮，**实测坐实了**：恢复代价 = `f(committed − applied)`，
  与日志总长无关。这是本场景唯一一条能改设计措辞的结论。
- **结论三（「8~10s」是有条件的，条件是攒批参数）**：见表。每段 1 条 txn 时 failover **101.2s**、
  10 条时 **16.9s**，都顶破 §5.4.4 承诺的窗口；**每段 ≥ 100 条**才回到 8s 附近。
  而「每段多少条」正是 §3.3 至今没定的那个数 —— **它不是吞吐调优项，是启动窗口的约束**。
  并行预取再省一个量级，但它买的是**延迟**：loopback 上只拿到 2.9×（本机瓶颈在 MinIO 服务端
  吞吐），真 S3 每跳 20–50ms、32 个请求同时在飞 ⇒ 那一列才是它的主场。
- **结论四（每段的固定开销 ≈ 1.31ms）**：与 L1 拟合出的 GET 截距 `a = 1.60–1.90ms` 同量级
  ⇒ 又一次印证「段对象是 KB 级，成本几乎全在截距上，字节数项可忽略」。
  这正是本场景开头那条运行时断言（段对象 1229B ≪ 64KB）在钉的东西。
- **结论五（恢复和 GC 是同一笔账）**：删掉 29967 个段对象要 14.52s，与顺序恢复同量级。
  ⇒ 「日志总长」不决定启动窗口，但它**决定 GC 的开销**，两者不能混着说。

**对设计的影响。**

- **§10.1 表第 3 行**：把「分析模型，非实测」改成实测结论（线性、比值 1/4/16、顺序最坏形态），
  并把「依赖 §3.3 还没定的攒批参数 ⇒ M4 定下来后复核一次」**换成一个具体门限**：
  **每段条数 ≥ 100**（M4 定攒批参数时把幕五那张表当约束看，而不是事后复核）。
- **§5.4.4 的「≈ 8~10s」要补前置条件**：它对「并行预取 **且** 每段 ≥ 100 条」成立；
  这两条任一不满足，第三项会从 ~1s 涨到 10~300s。
- **「有界」要分两种视图说**：`MAX_UNAPPLIED` 界定的是**热**视图（重启的 leader、落后不多的
  老副本，applied 水位就在几十万条以内）。**冷启动和新副本的 applied 停在 0，代价是 O(日志总长)**
  —— 22832 段在真 S3 上顺序读要十多分钟。设计里那句「恢复有上界」**没有区分这两者**，
  而 checkpoint / 日志压缩的**真正动机**是后者（前者靠旋钮就够）。
  这是 V4 顺带翻出来的一个缺口，建议在 §6.1 旁补一句。
- **「按列举恢复」这个对照组再次确认不值得**：8.26s vs 7.34s，捷径**更贵**（多 0.397s 的 list，
  而且每段仍要 GET），且还错（S5）。

**变异检查**（每条完整还原并复跑基线）

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| ① `recover_by_manifest` 不用直接 GET 定位段，改成先 `list` 一遍再挑 | 段数过千后 list 要翻页 ⇒ 超线性 ⇒ FAIL | ✅ `[FAIL]`，`对段数线性=false`，比值 3.9→**12.7**、16.1→**189.6**；`由applied水位决定` 也一并变 false |

- **「检查器自己需要被检查」已经成了本项目的常规动作**（S13 变异③ 的教训），所以这次先自查了
  线性断言的区间是怎么来的：它是 `ratio ∈ [0.65k, 1.5k]`，**k 来自设计比值 1/4/16、不来自实测值**
  —— 与 S13 那个「区间由被检对象自己的 min/max 生成」的恒真断言不同。
- **但变异① 暴露了这个检查的分辨率下限**：那条变异在**小规模上是线性的**（每段的前缀不超过
  1000 个 key 时，一次 list 就返回全量），只有阶梯里**超过 1000 的那一档**才看得见二次项。
  换句话说：**这一族错误需要 N > 1000 才逮得到** —— 如果阶梯最高只到 556 段，它会**悄无声息地
  通过**。所以 `RECOVER_BUDGET_SECS = 30s` 这个预算实际上是**检查分辨率**的下限，不是性能目标，
  不该为了跑得快把它压小。（变异① 为了跑得动临时压到 3s ⇒ 阶梯缩到 139/556/2224；
  即便如此，超过 1000 的那一档仍然抓住了它 —— 但 139→556 那一档的比值 4.0 落在带内，**没抓住**。）
- **幕五那张投影表是算出来的，不是测出来的**：本机只测了 loopback 的 1.31ms/段；真 S3 那两列
  是把每跳延迟换成 30ms、按 L1 的加性结论线性外推的。它成立的前提正是本场景开头那条断言
  （段对象 1229B ≪ 64KB）；一旦段对象变大（比如 §3.3 攒批攒到几 MB），传输项就回来了，表要重算。
- **单次 `recover_by_manifest` 是顺序的**，所以结论一测的是最坏形态；真实实现应当并发预取，
  幕三给了并发版的数字（2.9×），但**并发版没有进判定** —— 判定只钉线性与窗口两件事。

## S15 —— 视图求值 == etcd：随机事务序列两边对拍（含冷 key）

**被检验的假设。** 设计 §3.2 的立论是「compare 在 leader 内存视图上求值，于是提交路径不为每个
compare 发一次 GET」。§3.2.1 把它收紧成**逐 key 成立**：视图里没有这个 key 只等于「**还没人问过**」，
不等于「它不存在」，未命中要**回源一次**。

清单把这一条标成**承重墙**：视图替代不了 etcd 的话，§3.2 要重设计。所以本场景问的不是
「视图能不能用」，而是**「那一句收紧到底够不够」** —— 同一串事务喂给真 etcd 和 toy 的
「日志 + 树 + 视图」，两边必须处处一致。

**方法。** 三个设计决定，每一个都是为了让判定**有区分力**：

1. **对拍的另一边是真 etcd**，不是自己写的模型 —— 自己对自己的参照物会「两边错得一样」。
   etcd 是这套语义的上游定义（仓库的 OCC 照它做的：值比较、无 revision），拿它当参照物误差才有意义。
   `expect = None` 在 etcd 侧映射成 `Compare::version(key, Equal, 0)`（一个版本都没有 ⇒ 不存在）——
   这只是**向 etcd 问出同一个谓词**，不代表我们的存储有 revision。
2. **七成的 compare 写成「应当为真」**（拿树里的真实值当期望值）。四种 compare 里只有两格能分开
   「未命中当不存在」与「未命中回源」，而那两格都要求 key **在**（见下表）。做法既是真实 OCC 的形状
   （读过值、再拿它 CAS），也正好落在那两格上。
3. **前提显式计数**。`View` 分别记 `hits` / `misses` / **`misses_present`**（回源**读到了值**的 miss）。
   第三个是本场景的前提断言：它为 0 时本次对拍什么都没验到，而它会**照样打印 `[PASS]`**。

| 冷 key 上的 compare | "当不存在" | 回源 | 有区分力？ |
| --- | --- | --- | --- |
| `expect = None`，key 确实不在 | 真 | 真 | 否 |
| `expect = Some(x)`，x 是编的 | 假 | 假 | 否 |
| `expect = None`，key **在** | 真 | 假 | **是** |
| `expect = Some(真实值)`，key **在** | 假 | 真 | **是** |

对拍的三层：`View`（leader 内存视图，写穿 + 未命中回源）／`DurableStore`（对象存储上的有序分片 KV，
「树」的替身，range 的唯一来源）／`CommitLog`（复用 `src/commit.rs`，提交点 = Manifest 一次 CAS）。
冷 key 是**铺数据时故意造成的**：初始 128 个 key 只进树、不进日志、不进视图。

**实测**（`cargo run -- s15`，连跑三遍逐字节一致）

```
[PASS] s15 视图求值 == etcd：80 个 txn / 101 次 compare 两边逐条一致
        key 空间 128（4 个叶子对象 × 32）｜range [a/, e)
        分支判定：then 53 / else 27｜不一致 0
        视图记账：命中 50｜未命中 51｜**其中回源读到值 51**（有区分力的那一格）
        提交水位：实际提交 80 / manifest.committed_lsn 80
        最终状态：toy 99 / etcd 99 / 影子 99 个 key｜三者一致
        收尾：两边都清干净（各 0 个 key）
```

**结论。**

1. **§3.2 的立论成立**：视图上求值 compare、结果与 etcd 逐条一致（80 个 txn、101 次 compare、
   0 处分歧），最终状态三路一致，提交水位也与实际提交次数对得上。
2. **分界线不在「视图能不能替代 etcd」，而在「未命中那一步不能省」。** 51 次 compare 踩在
   从未被读过的 key 上，**每一次都回源读到了值** —— 这 51 次里只要有几次不回源，分支就会走错。
3. **`LeaderCachedKvBackend`（`cached_kv.rs:300-315`，遇 CAS 就 `invalid_key` 删键）不能当这个视图的
   模板。** 它是「视图答不上来就清掉、让读穿透」，而这里要的是「答不上来就**取一次权威值再答**」。
   两者在「key 不在视图里」这个输入上给出的答案不同，而这正是本场景的判定信号。
4. **回源的代价是稳态的，不是启动期的一次性开销**：只要 key 空间大于实际工作集，
   每个从未被问过的 key 第一次被问就要一行 GET。视图把「每 txn 每个 compare 一次 GET」
   降成「每个 key 一生一次 GET（前提是 leader 不换）」—— 这才是 §3.2.1 那句「逐 key 成立」的准确含义。
5. **一个 txn 内 compare 不短路**（全部求值完再选分支）在本场景里是刻意的：短路会让
   `misses_present` 这个前提计数失真。真实实现可以短路（分支结果不变），但那样就**看不出**
   「这次到底踩到几个冷 key」。

**变异检查（三条，每条完整还原后 `diff -q` 确认回基线）**

| # | 变异 | 预期 | 实测 |
| --- | --- | --- | --- |
| ① | `View::get` 未命中**不回源**，直接当"值不存在"（= `LeaderCachedKvBackend` 形状） | FAIL | **FAIL**：80 个 txn 里 **64 个**分支判定不一致；最终状态 toy 108 vs etcd 99；`misses_present` 从 51 掉到 **0**（前提断言同时报出来） |
| ② | `DurableStore::scan` 漏掉最后一个分片（模拟 range 组装出错） | FAIL | **FAIL**：被**起点**核对抓住（toy 96 vs etcd 128）—— 最早能抓住的地方 |
| ③ | `LeaderKv::txn` **不落树**，只写穿视图 | FAIL | **FAIL**：分支判定**全对**（视图是准的），只有**最终状态**抓住它（toy 128 vs etcd 99）⇒ 证明「落树」这一路是承重的，不是摆设 |

① 值得单独记一笔：它的第一处 mismatch 是 `expect: None` 落在**一个存在的 key** 上 ——
「当不存在」的实现答 `真`、正确实现答 `假`。这格在动手前**没有被我列进判定表**，
是变异跑出来的；表已经按实测补齐（见上文四行表）。

**诚实边界**

- **`DurableStore` 是「树」的替身，不是真 B-link 树**：按 key 首字节分片（4 个叶子对象 + 1 个目录），
  叶子不分裂。它存在的唯一目的是让 range **跨对象**（只读一个对象的 range 测不出组装错误）。
  树的布局、分裂顺序、父指针修复由 S2–S4 覆盖，本场景不重复验。
- **单写者**。提交点仍走 `CommitLog`（Manifest CAS），并发提交是 S6 的题目。
- **不验恢复**：视图从空开始，本场景不测「启动时从树 + 日志尾部重建视图」。
  所以「回源一次」这条只在**稳态**下被验到；冷启动那一格（视图为空 + 树里有全部数据）
  恰好就是本场景 ② 步的形态，但**只跑了 80 个 txn 就结束了**，没有测「冷启动 + 立即高并发」。
- **顺带发现（与本题无关，但对实现有用）**：`CasStore::list` **只返回一层**，而且返回的条目里
  混着 `.../tree/` 这种「目录」条目。`for key in list(prefix) { delete(key) }` 会**看起来清干净了** ——
  顶层对象真删了，嵌套的一层没碰，删「目录条目」还是无声的空操作。第一次跑就是收尾自检
  （toy 残留 99 个 / etcd 0 个）把它揪出来的。**任何要「列举整个前缀」的地方（GC 扫描、
  日志枚举、清场）都得自己往下走。**

## V5 —— 能力探测：两种「静默」的责任方相反

**被检验的假设。** S7 证明「MinIO 声明支持条件删除，实际发出去却被忽略」，S9 又证明**同一个后端**
的条件读是可信的。计划里 V5 要回答的是 S7 那句话能不能当**普适结论**用：
「被忽略」到底是这个后端的脾气，还是**我们所依赖的那个接口形状**本身有问题？
两者的处置完全不同 —— 前者换后端就好，后者换到哪都一样。

**方法。** 不信 `Capability` 位（S7 正是「位=true、行为=false」），**实发请求**：每个条件操作发
**一对** —— 正值让条件成立、负值让条件不成立。只发正值定位不了能力：一个**完全无视**条件头的
后端也会成功，看起来和真支持一模一样。

负值探测还多一条要求：**它自己的前提要显式检查**。负值靠一个「陈旧 etag」构造，如果那个 etag
其实不陈旧，条件恰好成立、请求「被拒」，于是无视条件头的后端也会被判成可信。所以探针里
`stale_is_stale`（`stale != fresh`）不成立就报 `VoidProbe`（「无效探测」），**不混进「可信」**。

**实测**（`cargo run --bin capability_probe`，连跑三遍一致，自建自清）

```
=== 能力探测（实发请求，不信 Capability 位）—— V5 ===
后端 scheme=s3｜探测前缀 toy/probe/（自建自清，可重复跑）

op                       declared  positive   negative   verdict
write_if_match              ✓  ok         Conflict   可信（条件生效）
write_if_not_exists         ✓  ok         Conflict   可信（条件生效）
read_if_none_match          ✓  ok         Conflict   可信（条件生效）
delete_if_match             ✓  ok         ok         危险：服务端静默忽略
delete                      —  ok         —          可用（无条件）
delete_batch + if_match     —  —          accepted   危险：客户端丢弃条件

注 delete_if_match：正值 ok（对象真的被删掉）**且**陈旧 etag 也被接受
   ⇒ 条件确实发出去了（单条删除走 `delete_once`，见文件头），是**服务端**没执行它。
注 delete_batch + if_match：两条都用陈旧 etag，仍被全部删掉。
   ⇒ 这一次观测本身分不出「客户端丢的」还是「服务端忽略的」——
     责任方是读 opendal 源码定的（`DeleteObjects` 请求体里没有条件头，见文件头）。

[WARN] 可以用：write_if_match、write_if_not_exists、read_if_none_match、delete
     必须绕开：delete_if_match（危险：服务端静默忽略）、delete_batch + if_match（危险：客户端丢弃条件）
     ⇒ 这就是 M1 启动自检的输出形状：**声明**与**实发**不一致时，以后者为准。
       两种「绕开」里，「服务端静默忽略」换后端会变（S3 支持单条条件删除），
       「客户端丢弃条件」换后端不会变 —— 那是 opendal 自己在最后一跳丢的。
     [OK] 自清干净：前缀 toy/probe/ 下 0 个对象
```

**结论。**

- **结论一（这一项真正要回答的）：「静默忽略条件」有两种，责任方相反。**
  - **服务端静默忽略**（`delete_if_match`）：条件随请求**发出去了**，服务端不执行。
  - **客户端静默丢弃**（`delete_batch + if_match`）：条件在**客户端**就被扔了，请求里根本没有它。

  证据不是这一次观测，是读 opendal 源码（下面两条）。区别在于**换后端之后**：前者换一个真支持
  的后端就好，后者**换到哪都一样**。
- **结论二：S7 的结论站得住，而且它是「服务端」那一类。** 单条条件删除走
  `BatchDeleter::flush_buffer` 的「缓冲只有 1 条」分支 → `delete_once`，它**明确设置了 `If-Match` 头**
  （`opendal-service-s3-0.59.2/src/core.rs:746`）。⇒ 请求确实带着条件到了 MinIO，是 MinIO 没执行。
  AWS S3 的单条条件删除是支持的 ⇒ **这一行换后端会变**。S7 不是 MinIO 的孤立怪癖，但也不是普适
  结论 —— 它是「本后端 + 单条路径」的组合。
- **结论三：批量路径丢条件是客户端行为，与后端无关（本轮新增的那条）。** 缓冲 ≥ 2 条时走
  `delete_batch`，`DeleteObjects` 的请求体**只序列化 `Key`/`VersionId`**（同文件 `:1385`），
  `if_match` 仅被用来分类**返回的错误**（同 crate `deleter.rs:100`）。`OpDelete` 一路上都带着这个
  条件（`opendal-core` 的 `raw/ops.rs:128`），是**最后一跳**丢的。
- **结论四：这与 opendal 自己的文档矛盾** —— `DeleteOptions` 写着 "OpenDAL never silently drops a
  condition"。**值得报上游**；对本项目则是硬约束（见下）。
- **结论五：「有检查层」≠「这条路被检查过」。** `CorrectnessCheckLayer::check_delete_args`
  （`layers/correctness_check.rs:84`）只核对 capability 位，对「条件被批量吞掉」一无所知。
  一个把 `if_match` 一路传到 `OpDelete` 的调用方，在它的视角里是**合规的**。
- **结论六：条件写全绿，坏的正好是 GC 需要的那个。** 四个非批量条件操作里三个可信
  （`write_if_match` / `write_if_not_exists` / `read_if_none_match`），唯一不可信的是**条件删除**
  —— 也就是说「用 `If-Match` 保证只删自己读到的那一版」这个想法，在这个后端上不成立。

**对设计的影响。**

- **硬约束：条件语义不许走批量路径。** 任何带条件的删除都必须单条发（`delete_with_if_match`），
  或者干脆换语义（走墓碑写、S7 已有结论）。批量删除只能用于**无条件**场景。
  这条以前靠「MinIO 会忽略」这个观察，现在有了**与后端无关**的依据 ⇒ 写进设计时不必再挂后端名。
- **M1 的启动自检判据是「实发」而不是 `capability()`**，输出形状就是这个探针的表：**可以用 / 必须绕开**。
  探针在独立前缀上自建自清，可以直接当启动自检用。
- **「跨厂商核对必须逐操作做」（S9 的结论）现在多了一个维度：责任方。** 危险行要按「换后端能修」
  （服务端类）和「换后端也修不了」（客户端类）分开记，混着看会把两种后果完全不同的事读成一件。
- **删除既然不可信，GC 的判据就不能是「条件删除成功」。** 这与 S7/S3 的既有结论一致，
  V5 的作用是把那条从「MinIO 怪癖」升格为「接口形状约束」。

**变异检查**（每条完整还原并复跑基线）

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| ① 让「陈旧 etag」不再陈旧（第二版写回**同样内容** ⇒ MinIO 的 ETag 是内容 MD5，S10 已证 ⇒ `stale == fresh`） | 前提塌了 ⇒ 三个用陈旧 etag 的行必须报「无效探测」，**不许**报「可信」 | ✅ `write_if_match` / `read_if_none_match` → **无效探测**。而且暴露了真实危险形状：`write_if_match` 那行的 negative 列**仍然显示 `Conflict`**（正值已把对象改成 v3，陈旧 etag 恰好真的不匹配了）⇒ 没有显式前提检查，这一行会**理直气壮地报「可信」** |
| ② `judge` 忽略负值（只看正值成不成功） | 一个已知会忽略条件的后端必须被判成「可信」⇒ 负值探测是承重的 | ✅ `delete_if_match` 从「危险：服务端静默忽略」翻成「**可信**」，而该行的 negative 列**自己写着 `ok`** |

**诚实边界。**

- **批量那一行，「这一次观测」本身分不出责任方**：陈旧 etag 被接受，既可能是客户端丢了条件，
  也可能是服务端忽略了它。责任方是**读源码**定的（结论三），不是这次请求测出来的。
  探针的输出里就写着这句话，免得读的人把推断当观测。
- **没有真 S3 可测**（本机无网络）⇒ 结论二里「换后端会变」这半是靠源码 + 契约**推断**的，
  只测到了 MinIO 这一侧。真正要下普适结论（比如写进设计的那句「S3 支持单条条件删除」）
  应当补一次真 S3 的探测。
- **探针只覆盖 s3 这一个 scheme**（本项目就用它）。换后端只需改 `cfg` 重跑，判定逻辑不用动。
- **探针自己也是「检查器」，所以按 S13 的教训先怀疑了它**：上面两条变异就是干这个的。
  其中变异①揭示的是**比预期更坏**的形态 —— 恒真的前提不会让检查报错，它让检查**照常给结论**。

## V6 —— 攒批：摊销倍数由什么决定

**被检验的假设。** 提交路径上每次提交要发两个请求（① PUT 日志段 ② CAS 推 Manifest 水位），
所以设计的想法是**攒批**：把 N 个 txn 的写并成一组落一段，于是「每 txn 2 次」变成「每组 2 次」。
V6 要回答三件事：

1. 摊销倍数到底是多少；
2. **这个倍数由什么决定** —— 是「攒批窗口」这个旋钮，还是别的什么；
3. 代价是不是延迟。

第 3 条是我自己先写错的：模块头一开始写的是「攒批不是更快的提交，是**用延迟换请求数**」，
实测把这句否掉了（结论三）。

**方法。** 三条臂**共用一份代码**（`src/group_commit.rs`），只差两个参数 `max_group` 与 `window`：

| 臂 | 参数 | 每 txn 请求 | 和前一臂差的是 |
| --- | --- | --- | --- |
| 逐条·每次读 | `CommitLog::commit` 原样 | put + cas + stat + get | — |
| 逐条·持 etag | `max_group = 1`，自己持 etag | put + cas | **读不读 Manifest** |
| 攒批 | `max_group = N` | 2 / 组 | **攒不攒批** |

两笔账分开算，免得把「缓存 etag 的功劳」记到「攒批」头上。

三个测量上的讲究：

- **逐条臂必须自己加锁。** 不加锁时 N 个写者读同一份 Manifest、只有一个 CAS 赢，
  而输的那些的段**已经落盘了** ⇒ 同一 `(epoch, lsn)` 被写了两份不同内容，
  正中 S6 那条「同一 lsn 内容必须唯一」。加锁 = 「leader 内部串行化」，是**没有攒批时最客气的做法**：
  请求数照旧线性增长，但不互撞。不加锁量到的会是 S6 的并发互撞，不是「重读 Manifest 的成本」。
- **请求数有两个独立来源**：攒批器自记的每组 (put, cas)，和进程级账本
  （`kv.rs` 的 `StoreOp` 计数，按**请求形状**分类 —— `write_if_not_exists` / `delete_if_match`
  都算 `Cas`）。两条路量同一个数，**对得上才算数**（P24 的教训：结论句不许写死）。
- **先判前提。** 攒批的收益只在「真的攒到了组」时发生，所以有独立一行
  「组大小中位数 > 1 的攒批臂有几条」——组大小恒为 1 时，"每 txn 请求数下降"这件事
  **根本没发生**，而账面照样能算出一个漂亮的比值来。

**「齐到」这个场景里攒批是白送的** —— 所有提交者一起发，同伴本来就排在队列里，
窗口调大调小都一样。所以另外加了一组**摊开到达**臂：提交者按固定间隔一个接一个来，
间隔取 200µs 与 2000µs（差一个数量级）。只有摊开之后，「窗口该调多大」这个问题才有数据。

**实测**（`cargo run --bin group_commit_probe`，自建自清；摊开臂复跑 3 次）

```

---  ------------------  -----  ----------------  ---------------------  ------------  -------  -------
1    逐条·每次读              1      1 / 1             1/1/1/1                4.00          10.2ms   10.2ms

复跑三次后，**可重复的是组数**（±1），不可重复的是组大小的分布（见“诚实边界”）。按组数报：

```
[V6] N=64 窗0ms —— 组数 / 每 txn 请求数 / 相对「逐条·持 etag」的倍数
        齐到            0µs/txn：  1 组  0.03  **64.0×**
        摊开到达        200µs/txn：  3 组  0.09  **21.3×**
        摊开到达       2000µs/txn： 17 组  0.53   **3.8×**
[V6] N=64 窗2ms —— 组数 / 每 txn 请求数 / 相对「逐条·持 etag」的倍数
        齐到            0µs/txn：  1 组  0.03  **64.0×**
        摊开到达        200µs/txn：  1 组  0.03  **64.0×**
        摊开到达       2000µs/txn：4~7 组 0.12~0.22   **9~17×**
```

**结论。**

- **结论一：请求账本两边对得上，且形状就是设计写的那样。**
  逐条·每次读 **4.00**（put+cas+stat+get）、逐条·持 etag **2.00**、攒批 **2 × 组数 / N**。
  攒批器自记的每组 (put, cas) 恒为 (1, 1)，与进程级账本逐条一致 ⇒ 「摊平」这件事
  确实发生在**落段**这一跳，不是记账好看。而且 N = 1 的三条臂全部是 2.00 ——
  攒批**没有**偷偷多花请求（窗口本身不产生请求）。

- **结论二：摊销倍数主要由「到达速率 vs 一次提交的往返时间」决定，不由窗口决定。**

  拿窗 0（也就是「不等，把已经排到的全收走」）看，**它照样攒到了**：

  | 到达间隔 | 组数 | 倍数 |
  | --- | --- | --- |
  | 齐到 | 1 | 64.0× |
  | 200µs | 3 | 21.3× |
  | 2000µs | 17 | 3.8× |

  组大小 ≈ 「一次提交的往返 ÷ 到达间隔」：提交要花 ~3.3ms（p50 214.8ms ÷ 64），
  这期间到达的 txn 全排在队列里，下一次 drain 一把收走。**这部分攒批是白送的，与窗口无关。**

  窗口只在**「到达间隔 ≈ 窗口」那一带**才是旋钮：

  - 200µs ≪ 2ms 窗口 ⇒ 窗 2ms 把 3 组并成 **1** 组（21.3× → **64×**）；
  - 2000µs ≈ 2ms 窗口 ⇒ 窗 2ms 只把 17 组降到 4~7 组（3.8× → ~9–17×），
    **远达不到 64×** —— 因为相邻两个到达之间就隔了 2ms，窗口收不到下一个同伴。

  ⇒ **窗口是边际旋钮，不是主旋钮。** 它能把「到达间隔与它可比」的那一档拉满，
  但拉不动「到达远慢于窗口」的那一档；后者要加窗口（拿延迟换），上限也只有 2 / 组。

- **结论三：「用延迟换请求数」是错的（至少不完整）。**

  | | 窗 0 | 窗 2ms |
  | --- | --- | --- |
  | N=1 p50 | 7.7ms | **12.2ms** |
  | N=64 p50 | 8.8ms | 10.0ms |
  | N=64 逐条·持 etag p50 | 214.8ms | — |

  低并发下窗口**确实**是纯加延迟（N=1：+4.5ms，等一个不会来的同伴）。
  但高并发下攒批**同时**降请求数（64×）**和**降延迟（p50 214.8ms → 10.0ms，**21×**）：
  逐条路径的延迟主要来自**串行化**（64 个提交排成一队，每个 ~3.3ms），
  而攒批恰恰把串行化去掉了；窗口那 ~2ms 的等待远小于省下的排队时间。

  正确的说法是：**攒批把「串行化的延迟」换成了「窗口的延迟」**，
  前者在高并发下远大于后者。只有并发度为 1 时它才是净开销。
  （摊开臂也印证窗口的延迟代价要显式记：2000µs·2ms 的 p99 47.9ms 对窗 0 的 16.6ms。）

- **结论四：一个组 = 一个 lsn ⇒ `committed_lsn` 数的是组数，不是 txn 数。**
  N=64 齐到时水位只推进 1。这在 toy 里成立是因为**日志段里没有 txn 边界**
  （S5/S6 已有的那层简化）；一旦 txn 边界要进日志，同组的 N 个 txn 就不能共用一个 lsn 了
  —— 这正是 V2b 要碰的那件事，本条是它的直接输入。

**对设计的影响。**

- **§3.3 的攒批参数：别把窗口当吞吐旋钮。** 摊销倍数主要由「提交并发度 ÷ 一次提交往返」
  给出，窗口只在到达间隔与它可比时才有意义。设计里若要写「窗口 = X ms」，
  应当同时写清它换到的是什么（低并发下的延迟），以及它买不到什么
  （把远慢于窗口的到达拉到高倍数）。
- **组大小 = 段大小** ⇒ V6 与 S16 是同一件事的两面：S16 说「每段 1 条时恢复要 101s」，
  这里说「到达间隔 > 提交往返时组大小就掉到 1~4」。
  ⇒ §3.3 的攒批参数是**启动窗口的约束**，不只是吞吐项。
- **单写者持 etag 是合法的**（S6 第二幕管的是**多个**写者共享一个陈旧 etag），
  但**逐条臂必须自己加锁**（方法节第 1 条）。这是**写 toy 时踩到的坑**，不是设计结论：
  第一版锁只包住了 lsn 自增、没包住提交，N=64 时 61 个写者 LostRace，
  且同一 lsn 的段被两份不同内容写过（debug-log P26）。

**变异检查**

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| 把 drain 从 `timeout(window, rx.recv())`（**先 poll 内层**）改成「先看时钟再看队列」（`if elapsed >= window { break }` + `try_recv()`） | 窗 0 全部退化成组大小 1 | ✅ 齐到·0ms 的 N=8/64 从 0.25/0.03 **翻回 2.00**（= 逐条·持 etag），摊开 200µs·0ms 与 2000µs·0ms 也**全部**翻回 2.00；而**窗 2ms 的臂大部分保住**（0.06 / 0.12 / 0.66）⇒ 承重的正是「窗 0 也在队列有货时取货」这条语义，不是「攒批」本身 |

而且变异版里**前提那一行自己报了 4/8**（基线 8/8）—— 这是「前提检查要能自己发现前提塌了」
的正确用法（P14 的教训）：我**没有**去读比值发现异常，是检查器自己报的。

**诚实边界。**

- **「一次提交的往返 ~3.3ms」是本机 MinIO 的数**，换真 S3 会变。
  而「窗口是边际旋钮」这条结论**依赖这个比值**（窗口只在与到达间隔可比时有意义）。
- **「摊开到达」是合成的到达过程**（固定间隔），不是真实负载。真实到达是泊松式的，
  组大小的分布会更散。
- **组大小中位数不可复跑。** 摊开·窗 0 那条臂三次复跑分出过 5/28、20/40、28/35 三种组大小，
  而**组数一直是 3**。所以报数时报**组数**（可重复，±1），别报组大小中位
  —— 探针把这句话印在输出上了。
- **N=1 的 p50 只有 1 个样本**，而且 ~7ms 里主要是 MinIO 的固定开销，不是攒批器的开销。
- 本机单机、loopback、无网络抖动；`瞬态重试 0 次`。
- 攒批器**不做背压**（通道容量 4096，提交者 `send().await` 直接排队）——
  「背压能不能收敛」是 V7 的事，这里刻意让它不成为变量。

## S17 —— 背压能收敛

> 跑法：`cargo run -- s17`（纯内存，不碰 store）。

**被检验的假设。** 设计 §6.1 说 applier 滞后时提交路径要**同步等**，等到水位回落到上限的一半。
计划里把它拆成三问：① 未 apply 量被压在上界内 ② 到上界后**返可重试错**而不是无限等 ③ **迟滞**回落能恢复。

**§6.1 不是「一个阈值」，是四件东西。** 这一点是写 toy 时才看清楚的 —— 少任何一件都不收敛：

| # | 要素 | 少了它会怎样 |
| --- | --- | --- |
| 1 | 上限 `MAX_UNAPPLIED` | 未 apply 量无界 ⇒ 恢复代价无界（S16 的结论） |
| 2 | 触及即**同步等** applier | 只报错不等 ⇒ 调用方只能自己轮询，把背压推给上层 |
| 3 | 等待**有超时**（返可重试错误） | applier 真停住时**无限等** ⇒ 死锁 |
| 4 | **迟滞**回落到一半才放行 | 在阈值上下抖动，每次抖动都要重排一次 |

**方法。** 关键不在负载，在**判定怎么写**。① 和 ③ 最自然的写法都是**恒真**的：

- ① 写「峰值 ≤ 上限」—— 那是控制器**自己的逻辑**推出来的（顶到上限就不放行），恒真（P14 / P16 那族）。
- ③ 写「放行点 ≤ 上限的一半」—— 那也正是代码写的。

所以两边各换了一种写法：

| 问 | 恒真的写法 | 换成什么 |
| --- | --- | --- |
| ① 有界 | 峰值 ≤ 上限 | **对照臂**：同样负载、`cap = ∞` 不拦，比峰值 |
| ③ 迟滞 | 放行点 ≤ 一半 | **拦截段数**（`episodes`）—— 迟滞真正防的是抖动 |

**对照臂顺带当了前提检查**：它若没超过上限，说明这个负载压根没造出压力，幕一测的就是一场空
（P16：恒真的前提不会让检查报错，它让检查**照常给结论**）。

幕二为什么是「applier 完全停住」而不是「慢 10 倍」：「慢 10 倍」逼不出无限等 ——
applier 只要真的在动，等待者终究会被叫醒。**只有一动不动时，「等待有超时」这条才承重。**

**实测**（三次复跑，段数与峰值一致）：

```text
[S17] 背压收敛：上限 100｜迟滞线 50｜超时 200ms｜applier 慢 10×
  幕〇·对照（同样负载，cap = ∞ 不拦）
        未 apply 峰值 2699｜放行 2834｜拦截 0 段
  幕一·有界（cap = 100）
        未 apply 峰值 100｜放行 208｜拦截 3 段｜等你 522 次｜超时 4 次｜迟滞放行点 [50, 50]
  幕二·applier 停住（水位填到 100，之后一次都不推进）
        [0..4] 等了 201~202ms → 可重试错 AtCap { unapplied: 100, cap: 100 }
  幕三·applier 恢复
        拦截 3 段｜迟滞放行点 [50, 50]（都该 ≤ 50）｜峰值 100
[PASS] s17 背压收敛: 上限 100｜峰值 100（对照不拦时 2699，27×）｜拦截 3 段（门限 8）
       ｜停住时 5 次全部在 202ms 内返可重试错（最久 202ms）｜恢复后放行点 Some(50)
```

对照臂的绝对值在 **2684~2699** 之间跳（合成负载的调度噪声），**27× 这个比值稳定**。

**结论。**

- **结论一：四要素全部成立，而且四要素缺一不可。** 「缺一不可」不是推断，是**变异检查分开验过的**
  （见下）。其中第 1、2 条的证据来自对照臂的 27×，第 3 条来自幕二，第 4 条来自段数。

- **结论二（★ 最有价值的一条）：迟滞有**两个**作用，第二个是设计里没写的。**
  变异①把 `release_below` 抬到与 `cap` 相等，期望是「迟滞没了、抖动起来」，实际打坏的是**上限本身**：

  ```
  变异① release_below = cap：峰值 101 > 上限 100，幕二里 applier 停住时也漏进去一个
  （等了 0ms 就放行），段数 132
  变异② release_below = cap - 1：上限守住（峰值 100）、幕二全返可重试错，
  只有迟滞那两条报火（段数 132、放行点 99）
  ```

  原因是拦截条件与释放条件**在取等时同时成立**：`unapplied + 1 > cap` 判定拦截，
  `unapplied <= release_below` 判定放行 —— 取等时刚进拦截态的那一瞬间 `unapplied == cap`
  就已经满足放行条件 ⇒ 立刻放行一个，`unapplied` 变成 `cap + 1`。

  两次变异刚好把迟滞的两个作用**分开**了：
  **(a) 让「未 apply 量 ≤ 上限」成为不变量 —— 这是安全属性，只有变异①能打坏它；
  (b) 防抖动 —— 变异①②都能打坏（都是 132 段）。**
  ⇒ **「严格低于」是结构约束，「低多少」只影响抖动频率**，两件事要分开写。

- **结论三：超时是真预算，不是摆设。** 幕二 5 次探测全部落在 201~202ms（预算 200ms），
  最短也 ≥ 100ms ⇒ 「等过」和「按时放弃」两件事都被测到了，
  而不是「秒返一个错」冒充超时（判定里 `stall_min_wait >= 预算/2` 就是防这个）。

- **结论四（附带观察，但会影响设计）：迟滞越深，排空越久，超时越多。**
  幕一在 applier **正常在动**的情况下也有 4 次超时 —— 排空到一半要 `50 格 × 10ms = 500ms`，
  超过 200ms 的等待预算。⇒ **拿到可重试错是预期内的，不是故障**；
  超时预算与迟滞线是**一对**参数，设计里应当一起定。

**对设计的影响。**

- **§6.1 补一行：释放线必须严格低于拦截线。** 设计写的「一半」本来就满足，
  但**为什么必须低**没写 ⇒ 实现时若有人为了「更快恢复」把迟滞调到 0，就把上限破了。
  这是一条**会被人无意踩掉的安全属性**，值得在文档里点明（玩具里靠变异检查才发现）。
- **超时预算与迟滞线一起写**（结论四）。§6.1 目前只有上限这一个数有明确量级。
- **§3.3 攒批与 §6.1 背压是串联的两级**，要写清谁先谁后（准入在入队前还是出队后、
  攒批的队列算不算未 apply 量）。设计里两节是分开的，toy 里这两个模块也**没有接起来** ⇒
  **这一条本场景没验**，只是指出它需要在设计里定下来。

**变异检查**

| 变异 | 期望 | 实测 |
| --- | --- | --- |
| ① `release_below = CAP`（迟滞线与拦截线取等） | 打坏迟滞（段数暴涨） | ✅ **同时打坏了上限**：峰值 101 > 100、幕二漏进一个（等 0ms 就放行）、段数 132 |
| ② `release_below = CAP - 1`（只留一格迟滞） | 打坏迟滞 | ✅ 上限守住（100）、幕二全返可重试错，**只**打坏迟滞两条（段数 132、放行点 99）⇒ 把「守上限」与「防抖动」两个作用分开了 |

两条都完整还原（`diff -q` 零差异、`grep -c MUTATION` = 0）。变异①挖出来的结构约束已写进
`src/backpressure.rs` 里 `BpConfig` 的文档注释 —— 那是它唯一能长期生效的地方。

**诚实边界。**

- **到达速率（4 个提交者每 1ms 一次）与应用速率（每 10ms 推一格）都是合成的**，不是真实负载。
  要验的是**形状**（有界 / 有超时 / 迟滞），不是绝对数 —— 上限在 toy 里取 100 而不是设计里的 10⁵；
  换成 10⁵ 只改一个常量，墙钟长 1000 倍而已。
- **控制器在进程内，`applied` 水位不写回 Manifest。** 真实实现里 applier 要 CAS 写 `applied_lsn`，
  那是个「两个写者 + `stat`→`read`」的问题（**S10 的题目**），这条成本没有进本场景的结论。
- 因此**没有覆盖**「背压与存储失败路径的交互」（例如 CAS 冲突后水位要不要回退、
  条件写失败时 `admitted` 已经加过了怎么办）。留给实现阶段。
- **幕二只做了 5 次准入。** 「不死锁」的证据是这 5 次都在预算内返回 + 幕三还能跑完，
  **不是**形式化证明（真要证得用模型检验，那超出 tiny toy 的范围）。
- 判定里的 `EPISODE_CEILING = 8` 来自「充满约 26ms + 排空到一半约 500ms ⇒ 一周期 ~526ms，
  1.5s 里约 3 段」的估算，实测 3 段 ⇒ 2.5 倍余量；对无迟滞的 ~150 段是 ~19 倍区分力。
- 单机、loopback、无网络抖动。

## L1 —— 节点大小（layout 参数）：这个决策比看上去轻

> 这是**唯一一个不是场景（S*）的条目** —— 它没有通过或不通过，产出的是**一条曲线加一组系数**。
> 跑法：`cargo run --bin layout_probe`，连跑三遍结果一致。

### 被检验的假设

> **节点大小**：对象存储按请求计费，节点越大 fanout 越高、depth 越浅、树遍历 GET 越少。
> 候选 64KB / 256KB / 1MB，用 `depth × 单跳延迟` 与 GC 粒度权衡。

候选值给出来了，但没有依据说该选哪个 —— 这正是要实测的部分。

### 方法：不建树，先拟合两个常数

整个决策只依赖

```text
单跳  t(N) = a + N/b          a = 请求固定开销（含 RTT），b = 有效带宽
查找  T(N) = hops(N) · t(N)
```

而 `a`、`b` **与树的结构无关**，所以不必等 B-link 树写出来就能测。探针做四步：

1. 在 MinIO 上扫 N ∈ {16K, 64K, 256K, 1M, 4M}，各 60 次取中位/99 分位，最小二乘拟合 `a`、`b`；
2. 注入 RTT 再扫一遍，**验证可加性**（见下）；
3. 把 `a`、`b` 代进树形，算 hops 与 T；
4. 对 D 做敏感性扫描 —— D 是唯一没测准的输入。

树形的递推（**叶子与内部节点的扇出不同**，两者容易混为一谈）：

```text
叶扇出 = N / 单条目字节      叶子存 key + value
内扇出 = N / 分隔键字节      内部节点只存 key + 子指针
叶数   = D / N               ← 与单条目字节无关，两者约掉了
hops   = 从根到叶读几个对象    单叶树 = 1，根 + 叶 = 2
```

代入的输入是**估算值**（来自对 meta 层 key 空间的清点，中等规模部署 ≈ 1000 表 × 10 region）：
`D ≈ 5MB`、单条目 ≈ 750B、分隔键 ≈ 48B。

### 实测

**① 拟合**（rtt = 0，loopback）

| | a | b | r² |
| --- | --- | --- | --- |
| PUT | 4.61–4.95 ms | 195–271 MB/s | 0.980–0.991 |
| **GET** | **1.60–1.90 ms** | **636–705 MB/s** | **0.968–0.984** |

（三遍的区间。**决策用 GET 那一行** —— 查找只读。PUT 慢一截是 MinIO 落盘的开销；
`b` 的 PUT 一列三遍散布最大（195 / 269 / 271），GET 一列只散布 ±5%。）

**交叉检验**：最小 N（16KB）的实测 p50 是 1.37–1.47 ms，其中传输项只有 0.023 ms ⇒ 它约等于纯 `a`。
拟合值偏大约 0.2–0.4 ms，说明模型有轻微曲率（大 N 端把截距拉高了）。
**斜率（b）不受这点曲率影响**，而决策靠的是 `b` 和 hops。

**② 可加性验证（带对照组）**

这一节是 loopback 数字能外推到真 S3 的**唯一依据**。关键在于**给 `sleep(rtt)` 本身也计时**：
不给 `sleep` 单独计时的话，注入 20ms 会实测差 22.4ms，多出来的 2.4ms 被容忍度吃掉 ——
等于**在用它自己证明自己**。

| 注入 | 纯 sleep 实测 | 残差（实测差 − 纯 sleep） |
| --- | --- | --- |
| 20 ms | 21.30 ms | 0.09 – 1.17 ms |
| 50 ms | 51.41 ms | 0.13 – 1.30 ms |

⇒ 残差 ≤ 1.4 ms、三遍一致 ⇒ **可加性成立**，§4 的表可以当真 S3 的预测读。

**③ 树形**（D = 5MB，单条目 750B，分隔键 48B）

| N | 叶扇出 | 内扇出 | 叶数 | hops | T@20ms |
| --- | --- | --- | --- | --- | --- |
| 16KB | 21 | 341 | 320 | **2** | 43.6 ms |
| 64KB | 87 | 1365 | 80 | **2** | 43.8 ms |
| 256KB | 349 | 5461 | 20 | **2** | 44.3 ms |
| 1MB | 1398 | 21845 | 5 | **2** | 46.6 ms |
| 4MB | 5592 | 87381 | 2 | **2** | 55.5 ms |

**全部候选都是 2 跳。** 16KB → 256KB 之间延迟差 0.7ms（1.6%）。

**④ 对 D 的敏感性**

| D \ N | 16KB | 64KB | 256KB | 1MB | 4MB |
| --- | --- | --- | --- | --- | --- |
| 5MB | 2 | 2 | 2 | 2 | 2 |
| 16MB | **3** | 2 | 2 | 2 | 2 |
| 64MB | **3** | 2 | 2 | 2 | 2 |
| 256MB | **3** | **3** | 2 | 2 | 2 |

两跳的硬上界 `D ≤ N² / 分隔键字节`：

| N | 16KB | 64KB | 256KB | 1MB | 4MB |
| --- | --- | --- | --- | --- | --- |
| 2 跳撑到 | 5.3MB | 85MB | 1.3GB | 21GB | 341GB |

**⑤ 序列化 CPU**（JSON，**悲观上界**；查找路径上只有 deser）

| N | deser 中位 | 查找 CPU（deser × hops） | 占 T@20ms |
| --- | --- | --- | --- |
| 64KB | 0.37 ms | 0.73 ms | 1.7% |
| 256KB | 1.47 ms | 2.94 ms | **6.6%** |
| 1MB | 6.0 ms | 12.1 ms | **26%** |
| 4MB | 24.0 ms | 48.0 ms | **87%** |

三遍的 256KB / 1MB 占比是 6.6/6.6/6.6% 与 26.0/25.4/25.4% —— CPU 这一项比 I/O 项稳定得多。

### 结论

**推翻的是「这是个需要权衡的取舍」这个前提。** 在这个项目的规模下：

1. **延迟上无差别**：16KB–256KB 全是 2 跳，差 0.7ms。要再省一跳得回到单节点（不可能）。
2. **写放大不花钱**：S3 的 PUT **按请求计费、不按字节**，而写放大正是通常拿来压制 N 的那一项 ——
   它在这里几乎不产生成本（存储本身 5MB 也是舍入误差）。真正随 N 变差的是 CPU 与 GC 粒度。
3. **真正的分水岭是 D 估计得准不准**：16KB 两跳只撑到 5.3MB，而估的 D 就是 5MB ——
   等于**没有任何余量**。D 一旦估错 3 倍，16KB 立刻掉到 3 跳（+22ms，+50%）；256KB 则要估错 260 倍。
4. **提交延迟完全不受这个参数影响** —— 日志模型下写路径是「1 次日志段 PUT + 1 次 Manifest CAS」，
   与 N 无关；节点大小只进入**读路径**与**异步 applier**。

⇒ **取 256KB。** 理由是拿字节换鲁棒性：延迟与 64KB 差 0.55ms，但抗 D 估算误差的余量是它的 15 倍，
而 CPU 占比 6.6% 仍属可忽略。**1MB 要等编解码换成 bincode/protobuf 之后才值得考虑**
（届时 CPU 项大约降一个量级，26% → 个位数）。

⇒ 两条对设计的要求：**做成配置项**（让使用者按自己的规模调）；
**编解码格式的选择要单独测一次** —— 它才是这个参数的上界，不是树。

### 诚实边界

- **D、单条目字节、分隔键字节都是估算，不是测出来的。** 来源是对 meta 层 key 空间的清点
  （`__table_info` ≈ 1.2KB/表、`__table_route` ≈ 190B/region 撑字节数，`__dn_table` 撑 key 数）。
  其中**每表 region 数与 `__dn_table` 的分散度是最不确定的两个量**。
  这也正是 §4b 那张敏感性矩阵存在的理由 —— 结论要能在 D 错一个量级时依然成立。
- **loopback 的 `a` 不代表 S3。** 外推靠的是 §3 的可加性验证（残差 ≤ 1.4ms），不是靠绝对值。
  真 S3 上 `a` 是 20–50ms，届时 hops 的权重比这里大得多 —— 但**结论方向不变，只会更强**
  （`a` 越大，`N/b` 这一项越无所谓，越是应该拿字节换 hops 余量）。
- **测的是单对象 PUT/GET 大 blob，不是真实节点。** 真实节点还有版本号、分隔键数组、
  右兄弟指针、条目定长/变长编码等，序列化形状不同；这一节的 `b` 是**传输带宽**，
  对 blob 和对真节点应当接近，但 CPU 项只对 blob 形状成立。
- **没测并发与 batch。** 只测了单线程串行单对象。批量写、并发读下连接池与 MinIO 的行为未覆盖。
- **JSON 的 CPU 是悲观上界。** 真实现用 bincode/protobuf 会显著更快更小，
  §5 的绝对值不可外推；能用的是它的**形状**（随 N 线性）和**占比能否忽略**这个判断。
- **没有真 S3 账号。** 上面 §4 的 T@20ms/50ms/100ms 是**外推值**，不是实测值。
  挂真延迟（toxiproxy / `tc netem`）重跑是把它变成实测的最短路径 ——
  探针已经支持 `--rtts=`，缺的只是一个能注入真延迟的链路。
